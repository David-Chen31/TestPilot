# TestPilot 设计决策

每个关键决策记录：做了什么、为什么、考虑过的备选方案。随里程碑推进补充。

## 0. 范围与里程碑（2026-10-19 调整）

### 0.1 为什么调整

目标岗位是大模型算法岗。原计划偏 Agent 工程（服务化、缓存、部署），缺少“提出假设 → 实验验证”的部分，也没有碰奖励 / 验证器。没有 GPU，所以不做大规模训练，把重心放到**奖励信号与验证器的设计和评估**上，这些只用 API 就能完成。

**2026-10-20 再次调整**：M5 之后按“算法面试官会追问什么”复盘，优先级改为 M5.5 → M8 → M9 → M10 → M11，M6 / M7 降级。理由：

1. **对比不公平**：B2 的 token 是 B1 的 2–4 倍，B2 更好可能只是因为花得多；也没有“覆盖率反馈”对照，无法支持“变异信号比覆盖率信号好”这个核心主张 → M5.5。
2. **样本太小**：1 个仓库、3 个文件、每格 3 次，没有置信区间 → M8 扩大规模。
3. **数据污染**：toolz 很流行，它自带的测试很可能在训练数据里（B0 在 itertoolz 上一次生成就有 89.5%）→ M8 加入晚于训练截止的仓库作对照。
4. **没有训练**：算法岗看重训练经验；“可验证奖励 → 奖励欺骗 → 推理时选择 → 用验证过的数据训练”是一条完整的主线 → M10 改为必做。
5. **相关工作**：MuTAP（2023，变异引导的 LLM 测试生成）、Meta TestGen-LLM（2024，过滤规则与本项目的有效性规则相近）、Meta ACH（2025，变异引导的测试生成）、CoverUp（2024，Python 覆盖率反馈）。本项目与它们的区别要落在实验上：等成本对照、奖励欺骗的量化、验证器用于选择与训练。
6. **M6 / M7 降级**：目标是单个文件，AST 已能拿到依赖，向量检索大概率没有收益；服务化对算法岗加分很少。

### 0.3 研究实验（M9）

1. **奖励欺骗分析**：去掉“原代码上必须通过”的约束，变异得分虚高多少？虚高来自哪些测试（原代码上失败 / flaky / 断言了错误行为）？对应作者此前 SWE-bench 复现测试审计的发现。
2. **测试时扩展**：每个目标采样 N ∈ {1, 2, 4, 8} 份测试，分别按 随机 / LLM 评委打分 / 变异得分 选择，画出效果随 N 变化的曲线。
3. **代理指标可靠性**：以变异得分为参照，覆盖率、LLM 评委打分与之的相关性。回答“哪个信号适合当奖励”。

### 0.4 模型选择

- 默认 `deepseek-flash`（最便宜的 DeepSeek 模型，2026-10 时由 DeepSeek-V4.1-Flash-1017 提供服务），通过 `.env` 可切换。
- **可复现性风险**：该别名无法锁定到日期版本，DeepSeek 升级后台模型会改变结果。应对：每次运行在日志中记录调用日期和响应返回的模型信息；同一组对比实验在尽量短的时间窗口内跑完。
- 正式评测前根据 M3 实测 token 用量估算总费用，确认后再大规模运行。

### 0.5 对照组（M5.5）

要回答的问题：B2 比 B1 好，是因为**变异信号**，还是因为**迭代更多、花的 token 更多**？

- **BC：覆盖率反馈**（`graph.py` 的 `BC`）。与 B2 同一张图、同样的终止条件和预算，同样先在原代码上跑 3 次、只用有效测试；区别只在反馈内容——B2 给存活变异体，BC 给有效测试没执行到的行和没走过的分支（`coverage_gaps`，带源码行）。提示词 `FEEDBACK_COVERAGE` 与 `FEEDBACK_MUTATION` 结构和措辞对齐。BC 与 B2 的差距 = 变异信号相对覆盖率信号的增益。
- **B0×N：等成本独立采样**（`agent/sampling.py`、`eval/selection.py`）。独立生成 N 份 B0 测试，两种用法，**都不使用变异信号**：
  - *best*：按“有效测试的行覆盖 > 分支覆盖 > 有效测试数”挑一份（并列取最早的）；
  - *union*：N 份样本里所有有效测试的并集。
- **N 怎么定**：取 N = 8，使 B0×8 的 token 在三个目标上都不少于 B2 的均值（B0 单次约 7.7K / 18.4K / 18.3K，×8 ≈ 62K / 147K / 146K；B2 均值 59K / 133K / 122K，见 m4_b0、m5_b2、m5_b2_d）。即对照组花的钱**不少于** B2。
- **样本都保存下来**（`samples/`、`screening.json`），M9 的测试时扩展可以离线换选择器（随机 / 变异得分 / LLM 评委）、取 N = 1, 2, 4, 8 的子集，不再调用 LLM。
- 进度分数加了分支覆盖率（排在行覆盖率之后），BC 需要它来比较“行覆盖相同、分支覆盖不同”的两轮。这会影响 B2 在并列时的取舍，因此 M8 所有方法都用同一版代码重跑，不和 M4/M5 的结果混在一张表里。

## 1. 沙箱（M1）

代码：`testpilot/sandbox/`

### 1.1 每个任务一份独立工作副本（`workspace.py`）

- **做法**：把仓库 `copytree` 到 `tempfile.mkdtemp()` 下，生成的测试、变异体都只写进副本，任务结束删除。
- **为什么**：Agent 会写测试文件，变异测试会改源码。直接在原仓库上操作，一次中断就可能留下被改坏的源码；多个任务并发时还会互相覆盖。
- **不复制** `.git`、`__pycache__`、虚拟环境、旧覆盖率数据：既慢，又可能让旧 `.pyc` / `.coverage` 干扰结果。commit hash 从原仓库读取，不需要副本里有 `.git`。
- **`symlinks=True`**：符号链接按链接复制，不跟随到仓库外，避免把仓库外的文件拷进来。
- **`resolve()` 路径检查**：所有读写都先解析到副本内，`../`、绝对路径、链接逃逸一律拒绝。之后 LLM 可调用的 `read_file` 等工具都经过这一层。
- **备选**：`git worktree`（要求是 git 仓库，且共享对象库）；overlay 文件系统 / 容器卷快照（更快，但依赖 Linux 特性，不便于本地开发）。仓库都是小型库，复制的成本可以忽略，选最简单的。

### 1.2 带超时、终止整棵进程树的子进程执行（`executor.py`）

- **问题**：`subprocess.run(timeout=...)` 超时后只 kill 直接子进程。如果被测代码起了孙进程，孙进程继续运行，并持有 stdout/stderr 管道，父进程读管道会一直阻塞，超时失效。
- **做法**：子进程用 `start_new_session=True` 自成会话（Windows 用 `CREATE_NEW_PROCESS_GROUP` + `taskkill /T`），超时时 `killpg(SIGKILL)` 整组终止。正常结束后也清理一次，防止测试留下的后台进程活过本次执行。
- **验证**：`tests/test_executor.py::test_timeout_kills_grandchild`。把终止进程树的逻辑替换成空操作后，这个测试在 Windows 和 Linux 容器里都会失败，说明它确实测到了这个行为。
- **已知漏洞**：孙进程如果自己 `setsid` 脱离进程组，`killpg` 杀不到。真正的隔离要靠容器 / cgroup（见 1.5）。

### 1.3 输出截断保留首尾

喂给 LLM 的报错按字符数截断，保留开头和结尾、丢中间：开头是命令 / 收集阶段的错误，结尾是最内层 traceback 和 pytest 汇总，中间多是重复的栈帧。截断处会注明省略了多少字符，避免 LLM 误以为输出是完整的。

### 1.4 pytest 结果用 JUnit XML 解析（`pytest_runner.py`）

- 终端输出格式随 pytest 版本和插件变化，XML 是稳定的机器接口，可以拿到逐用例的 通过 / 失败 / 错误 / 跳过 和失败信息。后续“有效测试 = 原代码上连续 3 次通过”需要逐用例结果。
- `-o addopts=` 忽略被测仓库配置里的 `addopts`（例如 `--cov`、`--doctest-modules`），避免因为缺插件导致跑不起来；`-p no:cacheprovider` 不在副本里写缓存。
- **没收集到测试不算通过**（`all_passed` 要求至少一个用例）。否则一个空测试文件会被当成“全部通过”。

### 1.5 生产环境还缺什么（本项目不做，但要知道）

当前的隔离只有“独立目录 + 进程超时 + 运行在 Docker 容器里”。被测代码和 LLM 生成的测试本质上是不可信代码，生产环境还需要：

- **每次执行一个一次性容器**（或 gVisor / Firecracker 这类更强的隔离），而不是在服务进程所在的容器里起子进程；
- **网络隔离**：`--network none`，防止测试代码外连或攻击内网（包括 Redis）；
- **seccomp / AppArmor** 限制系统调用，**非 root 用户**运行，**只读根文件系统**；
- **cgroup 资源限制**：CPU、内存、进程数（防 fork 炸弹）、磁盘写入量；
- 密钥隔离：当前 `sandbox_env()` 按变量名（含 KEY / TOKEN / SECRET / PASSWORD，以及 `REDIS_URL`）过滤掉子进程的环境变量，这是黑名单，容易漏；生产上应该用白名单，只传 `PATH`、`PYTHONPATH` 等必要变量，而且执行环境里根本不存在密钥。

### 1.6 Docker 构建的镜像源

宿主机走代理时，构建容器访问不到 `deb.debian.org`。Dockerfile 提供可选构建参数 `APT_MIRROR` / `PIP_MIRROR`（默认官方源），在 `.env` 里设置即可，不把某个国内镜像写死。

## 2. MCP 工具（M2）

代码：`testpilot/tools/`、`testpilot/sandbox/{coverage_runner,mutation,_mutmut_export}.py`、`testpilot/retrieval/ast_index.py`

### 2.1 每个任务一个 MCP server 进程（stdio），绑定一个工作副本

- **做法**：`python -m testpilot.tools.server --root <副本>`，Agent 端通过 stdio 连接。
- **为什么**：工具天然只能看到这个任务的副本，任务之间隔离；工具参数里不需要传仓库路径，LLM 也就没机会传错或越权。
- **备选**：一个常驻的 HTTP（streamable-http）server 服务所有任务，每次调用带 `job_id`。省掉进程启动开销，但要自己做任务到目录的映射和权限检查。任务是分钟级的，进程启动的几百毫秒可以忽略。
- **逻辑与协议分离**：工具逻辑写在普通类 `RepoTools` 里，`server.py` 只负责注册。单元测试直接测 `RepoTools`，另有一个端到端测试真的启动 server 子进程，走 MCP 协议调用工具。

### 2.2 工具集

| 工具 | 作用 | 输出控制 |
|---|---|---|
| `read_file` | 带行号读文件（可指定行范围） | 每次最多 400 行 |
| `list_symbols` | AST 列出函数 / 类 / 方法、行号、签名、调用的名字 | — |
| `search_code` | 字面量 / 正则搜索 .py 文件，找用法 | 最多 50 条 |
| `write_test_file` | 写生成的测试 | **只允许 `tests_testpilot/test_*.py`** |
| `run_pytest` | 运行测试，逐用例结果 | 只列出未通过的用例，信息首尾截断 |
| `coverage_report` | 目标文件的行 / 分支覆盖率、未覆盖行和分支 | — |
| `run_mutation` | 变异得分与存活变异体（行号、原代码、变异后代码） | 最多 20 个存活变异体 |

- **`write_test_file` 是规格外新增的**：让 Agent 的所有副作用都经过工具。只允许写进生成目录，因为 Agent 一旦能改源码，“测试在原代码上通过”就失去意义了。检查的是**解析后的真实路径**：`tests_testpilot/../sample/test_x.py` 字符串前缀合法，但实际会写进源码目录。单元测试抓到过这个 bug。
- 工具描述（docstring）用英文写，因为它是给 LLM 看的；代码注释用中文。

### 2.3 覆盖率

`coverage run --branch --include=<目标文件> -m pytest ...`，再用 `coverage json` 读取。行覆盖率 = 已执行语句 / 语句数，分支覆盖率 = 已走分支 / 分支数。覆盖率本身不区分测试是否通过，所以只对有效测试统计（由 M5 的有效性规则保证）。

### 2.4 变异测试（mutmut 3.8）

- **集成方式**：在副本的 `pyproject.toml` 末尾追加 `[tool.mutmut]`。`source_paths` 是目标所在的顶层包（mutmut 要把整个包复制到 `mutants/`，才能 import），`only_mutate` 把变异范围限制在目标文件，`also_copy` 声明生成的测试目录（mutmut 默认只复制 `tests/`）。每次运行前删除 `mutants/`，避免复用旧缓存。
- **结果导出**：mutmut 没有稳定的结构化输出，所以在副本目录里起一个子进程调用它的内部 API（`_mutmut_export.py`）。因此 mutmut 版本锁死为 3.8.0。
- **行号换算**：mutmut 的 diff 行号相对于函数开头。先用 AST 找到函数在原文件中的起始行（mutmut 把方法名改写成 `xǁ类名ǁ方法名`），再加上偏移；如果偏移不准（例如有装饰器），就在函数范围内按内容查找。单测验证了每个变异体的行号都能对上原文件内容。
- **得分口径**：`score = killed / (total − timeout − 无法编译)`。
  - `no tests`（没有任何测试执行到该变异体）算存活，不排除，否则不调用某个函数反而不扣分；
  - mutmut 用 libcst 生成变异体，语法总是合法的，所以“无法编译”恒为 0；
  - 其他非常规状态（suspicious、segfault 等）也排除出分母、单独计数，**不算作杀死**，避免得分虚高。
- **等价变异体**：样例 `clamp` 中，`if x < low: return low` 变成 `if x <= low` 后行为完全相同（`x == low` 时返回 `low` 等于返回 `x`），任何测试都杀不死。因此变异得分的上限低于 100%。单测 `test_strong_tests_kill_more` 明确断言了这两个存活者。评测时比较的是**同一目标上不同方法的相对得分**，等价变异体对各方法的影响相同。
- **规则**：变异测试的前提是测试在原代码上通过。mutmut 自己也会先在原代码上跑一遍，失败就拒绝继续，工具会把这种情况报成 error。M5 再加上“连续 3 次通过”的防 flaky 规则。
- **平台**：mutmut 依赖 `fork`，原生 Windows 上直接返回明确的错误；`pyproject.toml` 里按平台条件安装。

### 2.5 示例：覆盖率高 ≠ 能抓 bug

对样例 `sample/calc.py`，只断言 `clamp(5, 0, 10) is not None` 的弱测试：行覆盖率 70%，变异得分 1/7。补上边界值和错误信息断言后：行 / 分支覆盖率 100%，变异得分 5/7，剩下两个是等价变异体。见 `tests/test_repo_tools.py` 与 `tests/test_mutation.py`。

## 3. 基线 B0 与评测框架（M3）

代码：`testpilot/eval/`、`testpilot/llm.py`、`testpilot/prompts.py`

### 3.1 有效性规则的实现（`eval/metrics.py`）

- **计数单位是测试函数**：用 AST 数出测试文件里定义的 `test*` 函数和 `Test*` 类中的 `test*` 方法。按 pytest 收集结果计数的话，一个 import 就失败的文件会被算成“0 个测试”，而不是“N 个测试全部无效”，有效率会虚高。
- **有效 = 原代码上连续 3 次通过**。参数化测试的所有用例都通过，这个函数才算通过。第一次通过、后面失败的记为 flaky。某一轮之后已经没有候选测试时，提前结束。
- **覆盖率与变异得分只用有效测试计算**：把有效测试的 pytest nodeid 直接传给 coverage 和 mutmut。单测 `test_coverage_counts_only_valid_tests` 构造了一个“执行了全部分支但最后 `assert False`”的测试，验证它的覆盖率不被计入。
- **没有有效测试时**：覆盖率和变异得分记为 0，而不是缺失。否则“全部生成失败”的运行在求均值时会被悄悄丢掉。
- **单测级超时**：用 pytest-timeout 设 10 秒。在 Linux 上一个死循环测试只让自己失败，其他测试照常出结果。Windows 上 pytest-timeout 只能结束整个进程，这也是评测必须在 Docker 里跑的原因之一。
- **coverage 用空配置文件**：toolz 的 `[tool.coverage.run] source = ["toolz"]` 会让 `--include` 失效，覆盖率就不再只统计目标文件了。

### 3.2 评测仓库（`eval/repos.toml`、`eval/repos.py`）

- **固定 commit，下载 GitHub 的 commit 快照（tar.gz）而不是 git clone**：commit 写在 URL 里，内容确定；保留上游的 LF 换行（Windows 上 clone 会受 `autocrlf` 影响）。开发时 github.com 一度不可达，而 codeload 可以访问，这也是换方式的直接原因。解压用 `filter="data"`，防止压缩包里的 `../` 路径逃逸。
- **工作副本删除仓库自带的测试**（`remove` 字段）：B1/B2 的 Agent 能读文件、搜代码，不删的话它可以直接照抄已有测试。docstring 里的 doctest 示例保留，因为它们是源码的一部分，所有方法都能看到。

### 3.3 B0 与公共提示词

- B0 = 把目标模块的完整源码一次性交给 LLM，取回复中最长的 python 代码块作为测试文件，不运行、不修改。
- **所有方法共享同一份测试要求**（`prompts.TEST_REQUIREMENTS`）。B0 与 B1/B2 的差异只来自流程（一次生成 / 迭代修复 / 变异反馈），不来自提示词措辞，否则对比结果里会混进 prompt 工程的影响。
- 温度统一取 API 默认值 1.0：评测要求每个设置跑多次看方差，测试时扩展实验也需要采样多样性。

### 3.4 可复现性记录

每次运行的 `run.json` 记录以下信息：模型名、温度、`system_fingerprint`（模型别名不能锁定版本，用它记录后台实际版本）、token（含 cache 命中）、按高峰价估算的费用上限、生成和评测耗时、被测仓库 commit、TestPilot 自身 commit（`git describe --dirty`）。`trace.json` 保存完整的 prompt 和回复。

### 3.5 一次评测器 bug（已修复，结果已作废并保留）

第一批 B0 的变异测试全部没有执行。原因是 `also_copy` 传入了子目录中的单个文件，而 mutmut 复制单个文件时不创建父目录。单测只覆盖了“传目录”的情况，真实评测传的是有效测试的 nodeid。处理方式：
- 修复后补了回归测试；
- 汇总中显式记录 `mutation_error`，避免出错时只剩一个 `None` 得分；
- 第一批结果移到 `results/_discarded/m3_b0/` 并写明原因，整批重跑。

### 3.6 发现：deepseek-flash 默认会自适应思考，且 DeepSeek 不认 `max_completion_tokens`

- M3 之前我只用“回复 ok”这种极简请求做了测试（思考 token 为 0），由此**错误地**得出“默认不思考”的结论。复杂请求下它会自动思考：数到 300 用了约 500–1400 个思考 token。思考 token 计入输出、按输出价计费。
- langchain-openai 会把 `max_tokens` 改名为 `max_completion_tokens` 发送，而 **DeepSeek 忽略这个参数**，所以我设置的输出上限实际从未生效。
- 两者叠加的后果：B0 在 functoolz 的第 3 次运行中，模型一直思考到服务端上限 65,536 token，最终回复为空（`finish_reason = length`），生成 0 个测试。
- 修复：通过 `extra_body` 直接发送 `max_tokens`；思考模式可配置（`LLM_THINKING = auto / enabled / disabled`）；日志记录 `reasoning_tokens`。`tests/test_llm.py` 断言了请求体。
- **影响范围**：`results/m3_b0/` 与 `results/m3_b0_harder/` 都是在“思考 = auto、实际无输出上限（服务端 65,536）”的配置下得到的。这一点在它们的 `run.json` 中没有记录，以本节为准。

## 4. LangGraph Agent（M4）

代码：`testpilot/agent/graph.py`、`testpilot/agent/tool_client.py`、`testpilot/retrieval/context.py`、`testpilot/prompts.py`

### 4.1 图结构

```
START → plan → retrieve_context → write_tests → run_tests → analyze → decide ─┬→ write_tests（带反馈）
                                                                             └→ finalize → END
```

| 节点 | 做什么 | 用 LLM？ | 调用的工具 |
|---|---|---|---|
| `plan` | 确定要覆盖的公开 API | 否 | `list_symbols` |
| `retrieve_context` | 召回源码（带行号）、import 的定义、调用处，拼成提示词前缀 | 否 | `read_file` `list_symbols` `search_code` |
| `write_tests` | 第一轮写测试；之后根据反馈重写整个文件 | **是** | `write_test_file` |
| `run_tests` | 运行测试 | 否 | `run_pytest` |
| `analyze` | 全部通过时测覆盖率；计算进度分数、更新最好的一轮、生成反馈 | 否 | `coverage_report`（M5 加 `run_mutation`） |
| `decide` | 依次检查终止条件，决定继续还是结束 | 否 | — |
| `finalize` | 把分数最高的一轮写回测试文件 | 否 | `write_test_file` |

- **State（`AgentState`）**：目标、计划、提示词前缀、当前测试代码、最近一次 pytest 结果、覆盖率、变异结果、反馈、迭代次数、进度分数、最好的一轮、无提升轮数、token 用量、停止原因、轨迹。轨迹字段用 `operator.add` 作为 reducer，每个节点只追加自己的事件。
- **Node** 是 `TestPilotAgent` 的方法，**Edge** 除了 `decide` 之后的条件边都是固定边。
- **为什么不用 while 循环**：
  - 图把“有哪些步骤、步骤之间怎么走”显式写出来，终止逻辑集中在一个 `decide` 节点里；
  - 每个节点的输入输出都是状态的一部分，天然产生结构化轨迹；
  - M7 的 SSE 可以直接用 LangGraph 的流式输出；
  - 加一种反馈（M5 的变异测试）只需要改 `analyze`，不用改控制流。
- **为什么不是 ReAct**：ReAct 由 LLM 在每一步决定调用哪个工具。这里工具由节点确定性地调用，LLM 只负责写测试。代价是灵活性：LLM 不能主动去读某个文件。好处是：
  - 流程可复现，B0/B1/B2 之间只有反馈内容不同；
  - 不会把 token 花在“探索”上；
  - 终止条件可控。

  M6 之后可以考虑在 `write_tests` 内部开放 `read_file` / `search_code` 让 LLM 按需查阅，作为一个变体做对比。

### 4.2 B0 / B1 / B2 是同一张图的三种配置

- B0：`feedback = {}`、`max_iterations = 1`，只写一次。**B0 的提示词与 B1/B2 第一轮的提示词完全相同**（同样的上下文和要求），所以 B1 相对 B0 的提升只能来自反馈循环。M3 的 B0 只给了源码、没有召回上下文，也没有关闭思考；从 M4 起 B0 按新定义重跑。
- B1：`feedback = {"pytest"}`。反馈是失败用例的名字和断言信息，以及收集失败时的 pytest 输出。
- B2（M5）：再加上存活变异体。

### 4.3 终止条件（`decide`，按顺序检查，满足任一即停止）

1. 没有反馈（B0）：写一次就停。
2. 全部测试通过，且没有启用变异反馈：pytest 反馈已经没有可改进的地方。
3. 达到最大迭代数（默认 5 次 `write_tests`）。
4. token 预算用完（默认累计 30 万 token，每次 LLM 调用之后检查）。
5. 连续 N 轮进度分数没有提升（默认 N = 2）。

**进度分数**按字典序比较：`[全部通过, 变异得分, 行覆盖率, 通过的测试数]`。结束时 `finalize` 采用**分数最高的一轮**，而不是最后一轮，因为 LLM 重写整个文件时可能把原本通过的测试改坏。

### 4.4 提示词与缓存

- 每次请求 = 固定前缀（系统提示 + 带行号源码 + 召回的上下文 + 要求）+ 可变尾部（当前测试 + 反馈 + 任务）。DeepSeek 按前缀缓存，迭代时重复的部分按缓存命中价计费（约为未命中的 1/50）。
- **无状态提示词**：每轮只给“当前测试文件 + 本轮反馈”，不累积对话历史。上下文长度不随迭代增长，代价是 LLM 看不到自己前几轮的修改过程。
- 源码带行号：M5 的变异反馈会说“第 217 行的 `<` 改成 `<=` 后没有测试失败”，LLM 需要能对上行号。

### 4.5 工具接入

- 正式运行：每个任务启动一个绑定工作副本的 MCP server（stdio），用 `langchain-mcp-adapters` 的 `load_mcp_tools` 把它的工具加载成 LangChain 工具。
- adapters 遇到工具抛异常时不会向上抛，而是返回 `"Error executing tool ..."` 文本，客户端层把它转成 `ToolError`。
- 单元测试用 `LocalToolClient` 直接调用 `RepoTools`，逻辑相同。另有一个端到端测试，真的通过 MCP 运行整个 Agent。
- 每次工具调用都记录名字、参数摘要、耗时和是否成功，写进所在节点的轨迹事件。

### 4.6 思考模式：统一关闭

M3 发现 deepseek-flash 默认自适应思考，曾经思考到 65,536 token 上限也没有输出。从 M4 起所有方法统一 `thinking = disabled`，理由有三：
- 费用和耗时可控；
- 不再出现思考耗尽上限、没有任何输出的情况；
- B1/B2 的“思考”来自运行和反馈循环，关闭模型内部的思考后，提升能干净地归因到循环上。

“相同 token 预算下，模型内部思考 vs Agent 反馈循环谁更有效”留作 M9 的实验。

### 4.7 结果：B0 vs B1（toolz@451af60，每个设置每个目标 3 次，思考关闭）

均值 [最小, 最大]。来源：`results/m4_b0/summary.md`、`results/m4_b1/summary.md`。

| 目标 | 设置 | 有效率 | 行覆盖 | 分支覆盖 | 变异得分 | tokens / 次 |
|---|---|---|---|---|---|---|
| dicttoolz | B0 | 66.2% [0, 100] | 66.7% [0, 100] | 65.1% [0, 97.6] | 60.8% [0, 92.0] | 7.7K |
| dicttoolz | B1 | 100% [100, 100] | 100% [100, 100] | 97.6% [97.6, 97.6] | 92.9% [92.0, 94.9] | 7.8K |
| itertoolz | B0 | 99.1% [98.3, 100] | 94.9% [94.5, 95.0] | 91.8% [91.2, 92.9] | 89.5% [88.6, 90.4] | 18.4K |
| itertoolz | B1 | 100% [100, 100] | 95.6% [94.5, 97.2] | 94.3% [92.9, 95.3] | 91.0% [89.9, 92.4] | 35.2K |
| functoolz | B0 | 94.5% [92.5, 96.4] | 85.3% [79.7, 90.0] | 69.9% [64.6, 76.4] | 56.9% [50.9, 62.6] | 18.3K |
| functoolz | B1 | 100% [100, 100] | 86.5% [81.0, 89.3] | 70.6% [63.2, 75.0] | 58.6% [52.7, 62.4] | 74.0K |

结论（样本量小，只作为开发阶段的观察，正式结论见 M8）：

- **B1 的作用是“让测试能跑通”**：9 次运行全部 100% 有效，最多迭代 4 轮，全部因为“全部测试通过”而停止。B0 在 dicttoolz 上有 1 次因为一处语法错误（`def test_merge_with_single_iterable':`）导致整个文件无效，B1 的第一轮遇到同类问题时可以修复。
- **B1 几乎不提高覆盖率和变异得分**：itertoolz 和 functoolz 上，B1 与 B0 的范围大幅重叠。这符合预期，因为 pytest 反馈只告诉模型“哪里错了”，不告诉它“哪里没测到”，测试一旦全部通过，循环就结束了。这正是 M5 加变异反馈的动机。
- **修复是改断言还是删测试？** 统计了 5 次发生迭代的运行：失败的 29 个测试中 26 个被保留并修正，3 个被删除，同一轮也新增了 3 个。修正后的断言是否被“弱化”（例如改成 `is not None`），pytest 反馈本身无法发现，这是变异反馈要解决的另一个问题。
- **成本**：B1 在 functoolz 上平均 74K token，是 B0 的 4 倍。其中约一半是缓存命中（提示词固定前缀起了作用），按高峰价约 $0.03 / 次。

### 4.8 两个评测基础设施 bug（已修复）

1. **事件循环被关闭**：评测脚本原先每次运行单独 `asyncio.run()`，而 langchain-openai 在进程级缓存异步 HTTP 客户端，后续运行复用了绑在已关闭循环上的连接，间歇性报 `Event loop is closed`，第一批 B0 的 9 次运行中有 4 次失败。修复方式是整批共用一个事件循环。受影响的批次移到 `results/_discarded/` 并注明原因，整批重跑。
2. **无法解析的测试文件计数为 0**：语法错误时 AST 解析失败，“生成测试数”被算成 0，有效率变成 0/0。现在改为用正则按 `def test*` 计数（全部无效），并在无效原因里带上 SyntaxError。`results/m4_b0` 中 dicttoolz 的第 1 次运行是在修复之前评测的，它的“生成测试数”记为 0，实际写了约 60 个测试；有效数（0）、覆盖率和变异得分不受影响。

## 5. 变异测试反馈（M5，B2）

代码：`testpilot/agent/graph.py`（`analyze`、`_mutation_feedback`、`decide`）、`testpilot/prompts.py`、`testpilot/tools/repo_tools.py::check_validity`

### 5.1 流程

B2 与 B1 用同一张图，区别只在 `analyze`：

1. 有测试失败时，与 B1 相同，反馈 pytest 报错，先修到全部通过。
2. 全部通过后：
   - `check_validity`：在**未修改的原代码**上跑 3 次，只保留每次都通过的测试函数（有效性规则 4.2）；
   - `coverage_report` 和 `run_mutation` **只用有效测试**（传 pytest nodeid）；
   - 存活变异体以“`line N: 原代码 → 变异后代码`”的形式反馈，没有任何测试执行到的行会额外标注；
   - 不稳定的测试（跑 3 次里有失败）单独反馈，要求改成确定性的或删掉。
3. 进度分数 `[全部通过, 变异得分, 行覆盖率, 通过数]` 中的变异得分开始起作用，`finalize` 采用变异得分最高的一轮。

### 5.2 为什么变异打分前必须做有效性检查

- 一个在原代码上就失败的测试，在**每个**变异体上也会失败，mutmut 会把所有变异体记为“被杀死”，得分接近 100%，但这个测试什么也没验证。这正是 SWE-bench 复现测试审计中看到的虚高。
- flaky 测试是轻一些的同类问题：它会在一部分变异体上因为自身不稳定而失败，被误记为杀死。
- 所以 Agent 内部的打分和最终评测用同一份规则（`testpilot/eval/metrics.py::check_validity`），两边不会出现“Agent 以为提升了、评测却不认”的口径差异。

### 5.3 反馈里放哪些变异体

- 一次最多 15 个，避免反馈过长。从工具取回最多 200 个，再挑选。
- 排序规则：
  1. **没在反馈中出现过的优先**：展示过、仍然存活的，多半是等价变异体，或者模型确实无能为力，不应该每轮都占着反馈位置；
  2. **没有测试执行到的行**（mutmut 的 `no tests`）优先：这是最容易补的缺口；
  3. 按行号。
- 提示词明确告诉模型：有些变异体可能是等价的，跳过它们，不要为了杀死它们去写依赖实现细节的测试。这是为了防止模型为了“分数”写出脆弱的测试（例如断言字典键顺序）。

### 5.4 终止条件（在 M4 基础上）

- `feedback` 为空就停：B2 中表示“全部有效且没有存活变异体”，或者变异测试出错（停止原因中写明错误）。
- 等价变异体杀不死，所以 B2 通常会因为“连续 2 轮变异得分没有提升”而停止，而不是没有存活的变异体。
- 成本：每轮额外的本地开销是 3 次 pytest 加 1 次 mutmut。M4 评测中 mutmut 在 dicttoolz、functoolz、itertoolz 上分别约 9、22、43 秒，比 LLM 调用便宜得多。

### 5.5 安全：只读挂载评测代码

被测代码和 LLM 生成的测试在同一个容器里以 root 身份运行。原先 `./testpilot` 是可写挂载，测试代码理论上可以改写评测器本身，这是一个真实的 reward hacking 通道。现在 `./testpilot` 和 `./tests` 改为只读挂载。`./results` 仍然可写（评测要写结果），这是已知局限；生产环境应该每次执行用一个不挂载任何宿主机目录的一次性容器。

### 5.6 发现：B2 在 dicttoolz 上的提升，一部分来自“针对指标”的测试

B2 在 dicttoolz 上的变异得分为 99.5% [99.3, 100]（B1 为 92.9%）。逐个比对存活变异体：B1 的 3 次运行都剩下同样的 11 个，B2 杀死它们的方式分三类：

| 变异体 | 数量 | B2 怎么杀死的 | 判断 |
|---|---|---|---|
| line 14–15：`_get_factory` 报错信息被改 | 7 | 精确断言 `str(exc) == "dissoc() got an unexpected keyword argument 'bad'"` | **正当**：报错信息是对外可见的行为 |
| line 217：`dissoc` 的性能阈值 `len(keys) < len(d) * .6` | 3 | 传 `factory=OrderedDict`，断言结果的键顺序 | **灰色**：顺序可以观察到，但文档没有承诺；一个保持结果不变的性能重构就会让这些测试失败 |
| line 242：`assoc_in` 传给 `update_in` 的默认值 | 1（仅 run1） | `monkeypatch` 替换 `toolz.dicttoolz.update_in`，断言它收到的 `default` 参数 | **钻空子**：这个变异体在外部行为上严格等价，测试只是和实现绑死了 |

- 提示词里明确写了“可能存在等价变异体，跳过它们，不要写依赖实现细节的测试”，run1 仍然这样做了。run2、run3 没有，这两次 line 242 依然存活。
- 结论：**变异得分作为奖励信号是可以被钻空子的**。钻空子的方式不是写出“在原代码上失败”的测试（有效性规则已经挡住了），而是写出**和实现耦合的测试**：monkeypatch 被测模块的内部函数，或者断言未承诺的细节。这类测试在原代码上稳定通过，能杀死变异体，却会在合法的重构下失败，也不能多抓住真实的 bug。
- 这是 M9“奖励欺骗分析”的第一个真实案例。后续计划：
  1. 在评测中增加一个指标：**和实现耦合的测试数**（静态检查 monkeypatch / mock 被测模块自身的属性）；
  2. 比较“把这类测试计为无效”前后的变异得分；
  3. 考虑把“不得 patch 被测模块内部”加进有效性规则。

### 5.7 评测中断的根因：WSL 崩溃转储（以及一次错误的诊断）

- **现象**：B2 两次批量评测中途，容器全部报 `Connection error`，随后 Docker 守护进程无响应，C 盘空间被写满。
- **第一次诊断（错误）**：Windows 事件日志显示第一次故障前不久系统进入过新型待机，我据此认为是待机切断了网络，加了评测期间阻止待机的脚本。第二次故障时没有待机事件，这个解释站不住。
- **真正的根因**：mutmut 用 CPU 时间上限杀掉超时的变异体（itertoolz 中大量变异体会让无限迭代器陷入死循环），进程收到 SIGXCPU 后 core dump。Docker Desktop 基于 WSL，WSL 把每个 core dump 写到 Windows 的 `%TEMP%\wsl-crashes`，单个 0.1–1.9 GB，写入期间 WSL 虚拟机卡住。
- **证据**：
  1. 两次故障都从 B2 开始跑 itertoolz 的那一刻开始；
  2. 10 个 dump 全部来自 `python3.11`、信号 24；
  3. 在容器中手动触发一次 SIGXCPU 就能复现 Docker 卡死。
- **修复**：镜像中所有 Python 进程启动时通过 `.pth` 钩子设置 `PR_SET_DUMPABLE=0`（`docker/no_core_dump.pth`）。内核在任何形式的 core dump 之前都检查这个标志，fork 出的 mutmut worker 会继承它。`ulimit -c 0` 无效：WSL 用管道收集 core，内核不检查 RLIMIT_CORE，实测仍然产生了 dump。验证结果：
  - 触发 SIGXCPU 后退出码仍为 152，mutmut 照样判为 timeout；
  - 不再产生 dump，Docker 不再卡死。
- **兜底**：`eval.sh` 在评测前后报告 C 盘剩余空间和 dump 数量，新增 dump 时警告。阻止待机的脚本保留（待机确实会中断长时间评测），但它不是这次故障的原因。
- **教训**：第一次诊断只找到一个“时间上吻合”的事件就下了结论。正确的做法是先找能复现的机制。

### 6.2 结论（3 个目标，样本很小，只能当作假设，M8 验证）

1. **变异反馈的优势依赖目标，不是普遍成立。** itertoolz 上 B2 最好，但比 BC 只高 1.7 个点，区间重叠；dicttoolz 上 B2 高出很多，但 §5.6 已经说明其中一部分来自断言键顺序和一次奖励欺骗；**functoolz 上 B2 不如所有等成本对照**，甚至不如同样 token 的 B0×8 best（67.0%），比 union（74.4%）低 12 个点。
2. **覆盖率信号会饱和。** BC 在 dicttoolz 上第 2 轮就达到 100% 行覆盖 + 100% 分支覆盖，按规则停止，此时变异得分只有 91.0%：覆盖率说“没有可改进的了”，变异测试说还有 11–13 个变异体没杀死（137 个中）。这是“覆盖率不适合当奖励”的直接例子。
3. **在 functoolz 上，独立采样的多样性胜过迭代。** §5.8 已经看到 B2 在 functoolz 上大部分轮次在修失败的测试；把同样的 token 花在 8 次独立生成上，不同样本断言了不同的行为，并集自然杀死更多变异体。代价是测试集膨胀（约 660 个测试 vs B2 的约 100 个），测试运行和维护成本更高。
4. **因此下一步不是“B2 更好”，而是“变异信号用在哪里最划算”**：用于反馈（B2）、用于挑选样本（B0×N + 按变异得分选，M9 的测试时扩展），还是两者结合（先采样、再对并集做一轮变异反馈 / 按变异得分精简测试集）。样本已全部保存，M9 可以离线计算前两种，不需要再调用 LLM。

统计上：只有 3 个目标，配对符号翻转检验的最小可能 p 值是 0.25，**任何差异都不显著**。这正是 M8 要扩大目标数的原因。

### 6.3 B0×8 的 best 为什么几乎没有提升

best 按“有效测试的覆盖率”挑选（`screening.json`）。dicttoolz 上每份有有效测试的样本都是 100% 行覆盖、97.6% 分支覆盖，挑选退化成“有效测试数最多的一份”；itertoolz 上各样本行覆盖在 92–97% 之间，差别很小。best 在 itertoolz 上 90.7%，只比单次 B0（89.5%）高 1.2 个点。与结论 2 一致：覆盖率作为选择信号区分度不够。各样本单独的变异得分还没有算，M9 会在同一批样本上比较“按覆盖率选”和“按变异得分选”。

### 6.4 C 盘又少了约 7 GB：pagefile.sys 扩大

B0×8 批次期间 C 盘剩余从 9.0 GB 降到 2.1 GB，WSL 崩溃转储 0 个，C 盘上没有其他新写入的大文件；系统托管的 `C:\pagefile.sys` 为 19.1 GB，最后写入时间在批次运行期间。推断：评测反复复制工作区、mutmut 生成变异体，Linux 页缓存把 WSL 虚拟机的内存推到上限（默认为物理内存的一半），Windows 随之扩大页面文件。BC 批次（没有 union、样本少）期间 C 盘没有变化。

- 离线复现最重的一次评测（itertoolz union，约 900 个测试的变异测试），在 4 GB 内存上限下峰值 2.0 GB（cgroup `memory.peak`，含页缓存），没有 OOM，C 盘不再变化。
- 处理：`docker-compose.yml` 给评测容器加 `mem_limit: 4g`（页缓存计入 cgroup，超过后在容器内回收，不再推高虚拟机内存）；`scripts/eval.sh` 在开始 / 结束时报告 pagefile.sys 的大小。
- 没有改系统的页面文件设置（系统级配置，归用户决定）。系统托管的页面文件在重启后会恢复到初始大小。
- 局限：没有批次开始前的 pagefile 大小记录，“pagefile 扩大”是根据排除法和时间吻合得出的推断，不是直接观测。加上 eval.sh 的记录后，下一批可以直接确认。

### 7.5 一个评测 bug：union 被一份坏样本拖成 0

主批次第一版的 union 变异得分只有 64.7%，行覆盖 74.2%，**比它自己的子集 best（96.9%）还低**——并集的覆盖率不可能低于其中任何一份，这说明是评测出了问题，不是方法的性质。

- **原因**：union 把 8 份样本放进同一次 pytest 运行。只要其中一份有收集错误（语法错误、导入不存在的名字、导入时抛异常），pytest 就会中断整个会话，一个测试都不跑，其余样本的有效测试全部被判无效。16/64 个目标的 union 因此变成 0 个有效测试。M5.5 在 toolz 上没有暴露，只是因为那 24 份样本恰好都能收集。
- **修正**：union 只纳入单独筛查时至少有 1 个有效测试的样本文件（`selection.union_files`）。这与设计里“各样本有效测试的并集”的定义一致；单独筛查时就收集失败的文件本来就贡献 0 个有效测试。文件之间真实存在的相互干扰（例如一份样本在模块级改了全局状态）和整体超时仍然保留——它们是“把测试合在一起跑”的真实代价。
- **重评**：样本都已保存，用 `python -m testpilot.eval.rescore results/m8_main --tag m8_union_v2` 离线重评，不调用 LLM；原始日志 `m8_main` 不改动，比较时用 `--exclude b0n8-union` 排除第一版。
- **教训**：汇总表里的一个“不可能的数字”（子集比超集好）是发现 bug 的线索。报结果前要做这类一致性检查，而不是只看想比较的那一列。

### 7.6 结论与局限

1. **变异反馈有效，而且不只是因为多花了 token**：B2 显著优于 B1（+6.3）、覆盖率反馈 BC（+3.4，token 相近：70K vs 61K）、以及花得更多的 B0×8 best（+3.8，78K token）。M5.5 在 3 个目标上看到的“functoolz 上 B0×8 胜过 B2”在 66 个目标上不成立——小样本的结论确实不可靠。
2. **等成本的独立采样并集与 B2 打平**（+1.6，不显著），但需要约 6 倍的测试（445 vs 76），有效率也更低（90.1% vs 99.7%）。在“每个测试的杀伤力”上 B2 好得多；如果只看变异得分，“多采样 + 取并集”是一个同样强的基线。这正是 M9 要回答的：变异信号用于**选择 / 精简**（从并集里挑出能杀死同样多变异体的最小子集）能否同时得到两者的优点。
3. **在训练截止后创建的仓库上，反馈越重要**：new 组上 B0 掉了 15 个点，B1 掉了 16 个点，B2 只掉 4 个点；B2 相对 B1 和 BC 的优势在 new 组上大得多。一种解释是模型对熟悉的代码“记得”行为，对陌生代码更依赖执行反馈。但两组仓库的难度本身不同（人写测试在 new 组上也只有 56.6%），这只是相关，不能当因果。
4. **局限**：
   - 每个目标只跑 1 次，单个目标上的差异噪声很大，结论只在目标总体层面成立；
   - 4 个 new 仓库只有 17 个目标，而且领域偏（重试、LLM 输出处理），代表性有限；
   - 变异得分本身有上限和噪声（等价变异体，§5.6 的奖励欺骗）；没有人工检查 B2 的提升里有多少来自与实现耦合的测试——这是 M9 的第一项；
   - 人写测试的分数只包括在评测环境里能跑的部分，而且人写测试是针对整个包、不是针对单个文件的，比较只能作参照；
   - 3 次 B2 因为变异测试出错提前停止，boltons excutils / cacheutils 的部分评价因 mutmut 插桩干扰失败，这些运行不计入变异得分（按目标配对时自动排除）。
