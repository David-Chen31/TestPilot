# 里程碑面试题与参考答案

每个里程碑结束时的 3 道面试题，答案结合本项目的真实实现和 `results/` 中的真实数据。
回答时先给结论，再讲本项目怎么做的，最后说局限。文中的数字都能在对应文件里找到。

## M1：项目骨架、Docker、沙箱执行器

### Q1. 只用 `subprocess.run(cmd, timeout=10)`，被测代码又起了一个后台进程，会发生什么？你怎么解决？有没有解决不了的情况？

**会发生什么**：`subprocess.run` 超时后只 kill 直接子进程，然后调用 `communicate()` 等管道关闭。后台的孙进程继承了 stdout/stderr 管道，管道一直不关，父进程就一直阻塞，直到孙进程自己退出。所以超时形同虚设，而且孙进程会一直活着，泄漏资源。

**本项目的做法**（`testpilot/sandbox/executor.py`）：
- 子进程用 `start_new_session=True` 自成一个会话 / 进程组；超时后 `os.killpg(pgid, SIGKILL)` 把整组一起杀掉。Windows 上用 `CREATE_NEW_PROCESS_GROUP` + `taskkill /F /T` 按父子关系杀整棵树。
- **正常结束后也清理一次进程组**：测试留下的后台进程不能活过本次执行。
- 杀掉之后最多再等 5 秒读完管道（`_DRAIN_TIMEOUT`），防止仍被逃逸的进程卡住。
- **验证测试是有效的**：`tests/test_executor.py::test_timeout_kills_grandchild` 让子进程起一个“3 秒后写文件”的孙进程，1 秒后超时，再等 4 秒检查文件不存在。我把 `_kill_tree` 换成空操作再跑这个测试，Windows 和 Linux 上都会失败，说明它确实测到了这个行为，而不是碰巧通过。

**解决不了的情况**：
- 孙进程自己调用 `setsid()` 或 double-fork 脱离进程组，`killpg` 杀不到；
- Windows 上父进程先退出，孤儿进程就不在 `taskkill /T` 的树里了。

根本的解决办法是用 cgroup 或容器做边界：杀掉整个 cgroup，或者每次执行用一个一次性容器（PID namespace），进程怎么 fork 都逃不出去。

### Q2. 为什么“没收集到任何测试”（pytest 退出码 5）不能算通过？对变异得分有什么影响？

- `PytestRun.all_passed` 要求**至少有一个用例**，并且全部通过（`testpilot/sandbox/pytest_runner.py`）。
- 如果空文件也算“全部通过”：
  - **Agent 会被误导**：B1 的终止条件是“全部测试通过”，模型只要输出一个空文件，或者一个连测试都没定义的文件，循环就会以“成功”结束；
  - **指标失真**：有效率会变成 0/0，被当成 100%。
- 对变异得分的影响：变异测试只用有效测试。没有有效测试时，本项目把变异得分直接记为 0（`testpilot/eval/metrics.py::evaluate`），而不是“缺失”。否则“全部生成失败”的运行在求均值时会被悄悄丢掉，平均分虚高。同理，mutmut 里没有任何测试执行到的变异体（`no tests`）算存活，不从分母里排除，否则“干脆不测某个函数”反而不扣分。

### Q3. 被测代码在服务容器里以子进程运行，如果它是恶意的，能做哪些坏事？生产环境你会加哪三项隔离？

**本项目当前能做的坏事**（被测代码和 LLM 生成的测试本质上都是不可信代码）：
- **读取和外传数据**：容器有网络，可以访问外网，也可以访问同一网络里没有密码的 Redis（`redis:6379`）。子进程的环境变量已经过滤掉了密钥（`sandbox_env()`），但这是按变量名的黑名单，容易漏。
- **篡改评测本身**：docker-compose 把 `./testpilot`（评测代码）和 `./results`（结果）以可写方式挂载进容器，测试代码以 root 身份运行，理论上可以改写评测器或结果文件。这是一个真实的 reward hacking 通道。M5 中已把代码目录改为只读挂载，结果目录仍然可写，这是已知局限。
- **耗尽资源**：fork 炸弹、吃满内存或 CPU、写满磁盘，影响同一容器里的服务。

**生产环境的三项隔离**：
1. **每次执行一个一次性容器**（或者 gVisor / Firecracker 这类更强的隔离），并且 `--network none`、只读根文件系统、非 root 用户、不挂载任何宿主机目录。
2. **cgroup 资源限制**：CPU、内存、进程数（防 fork 炸弹）、磁盘写入量，外加墙钟超时。
3. **seccomp / AppArmor** 限制系统调用。密钥改用白名单环境变量：执行环境里根本不存在密钥，而不是“过滤掉已知名字的密钥”。

## M2：MCP server 与工具

### Q1. 只写 `assert result is not None` 的测试，为什么覆盖率可以很高、变异得分却很低？结合 `clamp` 说明。

- **覆盖率衡量“执行了哪些行”，不衡量“检查了什么”**。只要调用了函数，函数体的行就算覆盖；但 `is not None` 几乎对任何返回值都成立，代码被改错后断言照样通过。
- **变异测试衡量“改错了能不能发现”**：把 `<` 改成 `<=`、把字符串改掉之类，看是否有测试失败。弱断言抓不到这些改动，变异体就存活。
- **本项目的例子**（`tests/test_repo_tools.py`、`tests/test_mutation.py`，样例 `tests/fixtures/sample_repo/sample/calc.py`）：
  - 只断言 `clamp(5, 0, 10) is not None` 的弱测试：行覆盖率 70%，分支覆盖 50%，**变异得分 1/7**；
  - 补上边界值（`clamp(-1, 0, 10) == 0`、`clamp(3, 3, 3) == 3`）和错误信息断言（`pytest.raises(ValueError, match=...)`）之后：行 / 分支覆盖率 100%，**变异得分 5/7**。

  两份测试的覆盖率都不低，但抓 bug 的能力差了很多。

### Q2. 什么是等价变异体？它对变异得分有什么影响？为什么不影响 B0/B1/B2 之间的比较？

- **定义**：改动后程序行为（对所有输入）与原程序完全一致的变异体，任何测试都杀不死它。判断一个变异体是否等价，一般情况下是不可判定的。
- **本项目的例子**：
  - `clamp` 中 `if x < low: return low` 改成 `if x <= low`：`x == low` 时返回 `low` 和返回 `x` 是一样的；
  - toolz `dicttoolz.py` 第 242 行，`assoc_in` 传给 `update_in` 的默认值被改成 `None`，但这个默认值只会传给一个忽略参数的 `lambda x: value`。
- **影响**：变异得分的上限低于 100%。比如 M3 中 dicttoolz 剩下的 4 个存活变异体在 3 次运行中完全相同，全是等价或近似等价的，B0 已经到顶（97.1%）。
- **为什么不影响比较**：所有方法在**同一个目标、同一组变异体**上打分，等价变异体对每个方法都存活，相当于给所有方法的分母加了同一个常数，排序不变，只是绝对值被低估。
- **要补充的细节**：有“近似等价”的变异体。dicttoolz 第 217 行是个性能优化阈值，改了只影响结果字典的**键顺序**，用 `==` 比较观察不到，但如果测试断言 `list(result)` 的顺序就能杀死它。这类变异体对不同方法不完全公平。更严格的做法是人工标注等价变异体，然后只在“可杀死的变异体”上计分。

### Q3. MCP server 为什么设计成“每个任务一个 stdio 进程”，而不是常驻 HTTP 服务？各自的代价？

| | 每任务一个 stdio 进程（本项目） | 常驻 HTTP 服务 |
|---|---|---|
| 隔离 | 进程启动时就绑定到这个任务的工作副本（`--root`），工具只能看到这一个目录 | 需要自己维护 job_id → 目录的映射，并在每次调用时做权限检查 |
| 参数 | 工具参数里不需要仓库路径，LLM 没机会传错或越权 | 每次调用都要带 job_id |
| 生命周期 | 随任务启动和结束，任务结束进程就退出 | 常驻，要处理会话超时和资源回收 |
| 代价 | 每个任务付一次进程启动开销（Python 导入，约 1 秒）；任务之间不能共享缓存；并发任务多时进程也多 | 启动开销只付一次，可以跨任务共享缓存，可以远程部署 |

任务是分钟级的，1 秒的启动开销可以忽略，而隔离和简单性更重要，所以选了 stdio。如果要做成多租户的远程服务，或者单次工具调用很频繁、很便宜，就该换成 HTTP（streamable-http），并补上鉴权。

## M3：基线 B0 与评测框架

### Q1. 有效测试为什么要求“原代码上连续 3 次通过”？只跑 1 次，哪类测试会混进来，怎样影响变异得分？

- **混进来的是 flaky 测试**：依赖随机数、当前时间、执行顺序、共享状态、哈希顺序、网络的测试，偶尔失败。
- **对变异得分的影响**：变异测试时，这类测试会在某些变异体上**因为自身不稳定而失败**，mutmut 就把那些变异体记为“被杀死”，其实与变异无关，**变异得分虚高**。这和“原代码上就失败的测试会杀死所有变异体”是同一类问题，只是程度轻一些。
- **为什么是 3 次**：如果一个测试每次通过的概率是 p，跑 1 次混进来的概率是 p，跑 3 次是 p³。p = 0.8 时，从 80% 降到约 51%。
- **本项目的实现**（`testpilot/eval/metrics.py::check_validity`）：
  - 记录“先通过、后失败”的测试为 flaky；
  - 单测 `test_validity_detects_flaky` 用一个计数文件模拟了“第一次通过、之后失败”的测试。
- **局限**：
  - 3 次固定顺序运行，抓不到**顺序依赖**型的 flaky（单独跑通过、和别的测试一起跑失败）。可以用 `pytest-randomly` 打乱顺序跑；
  - 失败率很低的 flaky 仍可能混进来。

### Q2. dicttoolz 上 B0 已经是 97.1%，剩下的全是等价变异体。拿它证明“B2 比 B0 好”会得到什么结论？评测目标该怎么选？

- **会得到“没有差别”**：B0 已经到达这个目标的有效上限（3 次运行剩下的 4 个存活变异体完全相同，见 `results/m3_b0/`），B2 最多和它持平。但这个结论**不是因为 B2 没用，而是目标饱和了**，测量工具分辨不出差别，这就是**天花板效应**。
- **怎么选目标**：
  1. **基线没有饱和**：先跑 B0 看有没有提升空间。M3 就是这样发现 dicttoolz 饱和、functoolz 只有约 57%（M4，思考关闭）；
  2. **难度分层**：在简单、中等、困难的目标上分别报告，而不是只报总均值，否则一个饱和的目标会稀释差异；
  3. **避免数据污染**：toolz 很有名，模型可能见过它自带的测试。M8 计划加入模型训练截止之后才创建的仓库做对照；
  4. **样本量**：每个设置至少 3 次，报告范围，正式评测扩大到约 100 个目标函数并做显著性检验。

### Q3. 结果表里有一次运行生成了 0 个测试，原因是什么？从均值里去掉合理吗？

- **原因**（`results/m3_b0_harder/b0/toolz/functoolz/run3/trace.json`）：`finish_reason = length`，completion 65,536 token，回复内容为空。两个问题叠加：
  1. deepseek-flash **默认自适应思考**，复杂任务下会大量思考。我起初用一个极简请求探测，思考 token 为 0，就错误地得出了“默认不思考”的结论；
  2. langchain 把 `max_tokens` 改名为 `max_completion_tokens` 发送，而 **DeepSeek 忽略这个参数**，我设的 16K 上限从没生效。模型一直思考到服务端上限 65,536 token，也没有输出答案。
- **能不能去掉**：**不能悄悄去掉**。要区分两类失败：
  - **方法本身的失败**（例如 B0 写出了语法错误的文件）：必须保留，计为 0 分，这是方法的真实表现。只报成功的运行，就是挑结果；
  - **配置 / 基础设施的问题**（这次就是）：应该修复配置，然后**整批重跑**，而不是只去掉坏的那一次。被替换的批次保留在 `results/_discarded/` 里并写明原因。M4 的“事件循环被关闭”也是这样处理的。

  另外，要报告“运行次数 / 成功次数”和最小值，让读者看到失败的存在。

## M4：LangGraph Agent（B1）

### Q1. 你的 Agent 和标准 ReAct 有什么区别？为什么选择“固定的图 + LLM 只写代码”？放弃了什么？

- **ReAct**：LLM 每一步输出“思考 + 行动（调用哪个工具、什么参数）”，观察工具结果后再决定下一步，控制流由 LLM 决定。
- **本项目**（`testpilot/agent/graph.py`）：控制流是一张固定的 LangGraph 图：

  ```
  plan → retrieve_context → write_tests → run_tests → analyze → decide → write_tests / finalize
  ```

  工具由节点**确定性地**调用，LLM 只在 `write_tests` 里出现，职责是“根据上下文和反馈写出整个测试文件”。
- **为什么这样选**：
  1. **可复现、可对比**：B0/B1/B2 是同一张图的不同配置，差别只在反馈内容。ReAct 的探索路径每次都不同，难以归因；
  2. **成本可控**：LLM 不会把 token 花在“读哪个文件”这种探索上；
  3. **终止条件显式**：集中在 `decide` 节点，面试官问到时能逐条说清楚；
  4. **该确定的事不交给模型**：要测哪些函数用 AST 就能确定（`plan`），上下文召回也是确定性的（`retrieve_context`）。
- **放弃了什么**：灵活性。LLM 不能主动去读它想看的文件，例如 functoolz 内部用到的 `_signatures` 模块没进上下文，模型也没法自己去查。改进方向是在 `write_tests` 内部开放 `read_file` / `search_code`，让模型按需查阅，作为一个变体和固定流程做对比。

### Q2. B1 的覆盖率和变异得分几乎没超过 B0，为什么？对设计 B2 有什么启发？

- **数据**（`results/m4_b0/summary.md`、`results/m4_b1/summary.md`，各 3 次）：

  | 目标 | B1 有效率 | 变异得分 B0 | 变异得分 B1 |
  |---|---|---|---|
  | functoolz | 100% | 56.9% [50.9, 62.6] | 58.6% [52.7, 62.4] |
  | itertoolz | 100% | 89.5% [88.6, 90.4] | 91.0% [89.9, 92.4] |

  9 次运行有效率全部 100%，而 B0 是 66%–99%。但两边变异得分的范围大幅重叠。
- **原因**：pytest 反馈只说“哪里**错了**”，不说“哪里**没测到**、哪里**测得不够强**”。B1 的终止条件是“全部通过”，一旦通过循环就结束，没有任何信号推动它补测试。另外，修复失败测试时有可能把断言改弱（改成能通过的样子），pytest 反馈对此完全无感。
- **对 B2 的启发**：
  1. 要给“测得不够”的信号，即存活变异体。它直接指出“第几行改成什么样之后，没有测试发现”，比“第几行没覆盖”更具体，也能惩罚弱断言；
  2. 测试全部通过之后循环要能继续，终止条件变成“没有存活变异体 / 连续 N 轮变异得分不提升 / 预算用完”；
  3. 变异打分只能用有效测试（原代码上连续 3 次通过），否则 flaky 或失败的测试会虚高得分。

### Q3. 为什么结束时采用“分数最高的一轮”而不是最后一轮？进度分数为什么按“全部通过 > 变异得分 > 覆盖率 > 通过数”排序？

- **采用最好的一轮**：每一轮 LLM 都会**重写整个文件**，可能把原本通过的测试改坏，或者删掉有用的测试，所以最后一轮不一定最好。`finalize` 节点把分数最高的那一轮写回去（`tests/test_agent.py::test_stops_without_improvement_and_keeps_best_round`：第 1 轮最好，后两轮更差，最终采用第 1 轮）。另一个原因：“连续 N 轮没有提升”触发停止时，最后几轮恰好都不是最好的。
- **排序的理由**（`progress_score`，按字典序比较）：
  1. **全部通过**最优先：有失败的测试时，覆盖率和变异得分都不可信（变异只在有效测试上算），先保证能跑通；
  2. **变异得分**其次：它是最终要优化的指标，最直接地衡量“能不能抓 bug”；
  3. **行覆盖率**：变异得分相同时，覆盖更多的代码更好（B1 不算变异得分时，靠它区分）；
  4. **通过的测试数**：前面都相同时，用来区分还没全部通过的两轮，例如 7 个失败的一轮不如 1 个失败的一轮。
- **注意**：字典序意味着“1% 的变异得分提升”胜过“覆盖率提升 20%”，这是有意为之。如果想在两者之间做权衡，可以改成加权和，但权重本身又需要调，会引入新的超参数。

## M5：变异测试反馈（B2）

### Q1. 为什么在做变异测试前，Agent 要先把测试在原代码上跑 3 次？如果直接拿当前测试去做变异测试，会怎样？

- **会虚高**。一个在原代码上就失败的测试，在每个变异体上也会失败，mutmut 会把所有变异体都记为“被杀死”，变异得分接近 100%，但这个测试什么都没验证。flaky 测试是程度轻一些的同类问题：它会在一部分变异体上因为自身不稳定而失败。
- **对 Agent 来说更危险**：变异得分是 B2 的优化目标（进度分数的第二位）。如果不过滤，Agent 会从反馈里“学到”写失败的测试也能涨分，这就是给了它一个钻空子的通道。
- **本项目的做法**：`analyze` 在测试全部通过后调用 `check_validity` 工具（原代码上跑 3 次），只把每次都通过的测试的 nodeid 传给 `coverage_report` 和 `run_mutation`；不稳定的测试单独反馈，要求改成确定性的。Agent 内部打分和最终评测用的是同一份规则（`eval/metrics.py::check_validity`），口径一致。
- **mutmut 自己的检查不够**：mutmut 会先在原代码上跑一遍测试，有失败就拒绝继续。但它只跑一次，挡不住 flaky 测试；而且它是“拒绝整批”，不会告诉你哪些测试可用。

### Q2. B2 在 dicttoolz 上把一个“严格等价”的变异体也杀死了，它是怎么做到的？这说明变异得分作为奖励有什么问题？怎么防？

- **怎么做到的**（`results/m5_b2/b2/toolz/dicttoolz/run1/test_dicttoolz.py`）：line 242 的变异把 `assoc_in` 传给 `update_in` 的默认值从 `value` 改成 `None`，而这个默认值只会传给一个忽略参数的 `lambda x: value`，外部行为完全相同。模型用 `monkeypatch` 把 `toolz.dicttoolz.update_in` 替换成一个记录参数的假函数，然后断言 `default == 42`。提示词里明确写了“跳过等价变异体，不要依赖实现细节”，它还是这么做了（3 次运行中的 1 次）。
- **说明的问题**：变异得分作为奖励信号可以被钻空子。有效性规则挡住了“写失败的测试”这条路，但挡不住**和实现耦合的测试**：它在原代码上稳定通过，能杀死变异体，却会在合法的重构下失败，也不能多抓住真实的 bug。这是“奖励 ≠ 真实目标”的典型例子，和 SWE-bench 复现测试的虚高是同一类问题，换了一种形式。
- **同一批里的灰色地带**：line 217 的 3 个变异体是通过断言 `OrderedDict` 的键顺序杀死的。顺序可以观察到，但文档没有承诺。这类测试比 monkeypatch 好一些，但同样脆弱。
- **怎么防**：
  1. **静态检查**：测试中 monkeypatch / mock 被测模块自身的属性，计为“与实现耦合”，不参与变异打分，或者在奖励里扣分；
  2. **只通过公开 API 交互**：把这个约束写进有效性规则，而不只是写在提示词里（提示词约束已经被证明不可靠）；
  3. **人工标注等价变异体**，从分母里去掉，模型就没有动机去杀它们；
  4. **用多个信号交叉验证**，例如在一批人工注入的真实 bug 上看检出率，而不是只看变异得分。

### Q3. 为什么 B2 在 functoolz 上提升有限？你会怎么改？

- **数据**（`results/m5_b2_d/`）：functoolz 上 B2 为 62.4% [57.1, 67.2]，B1 为 58.6% [52.7, 62.4]，范围重叠。itertoolz 上 B2 为 95.8% [93.1, 98.7]，稳定高于 B1 的 91.0% [89.9, 92.4]。
- **原因：迭代预算被修测试占掉了**。functoolz 的 3 次运行共 15 轮，只有 4 轮测试全部通过、拿到了变异反馈，其余 11 轮在修失败的测试。轨迹是“失败 → 失败 → 57.8% → 失败 → 67.2%”：模型为杀变异体新加的测试经常在原代码上就失败（`curry`、`memoize`、签名推断的行为细节很难猜），下一轮又得回去修。而且所有运行都是因为达到最大迭代数 5 而停止的，预算明显是瓶颈。
- **改进**：
  1. **增量模式**：变异反馈轮只追加新测试、不重写旧测试；新测试在原代码上失败就直接丢弃，不进入修复轮。这样已经通过的测试不会被改坏，预算也不会被修复占掉；
  2. **分开预算**：修复轮和变异轮分别计数；
  3. **按函数拆分任务**：functoolz 有 1100 多行，一次重写整个测试文件，输出长、出错面大。按函数或类分别生成和反馈，每次改动更小；
  4. **给模型查阅能力**：`curry` 依赖 `_signatures` 模块，它不在上下文里。允许 `write_tests` 调用 `read_file`，可能减少“猜错行为”导致的失败。

## M5.5：对照组（覆盖率反馈 BC、等成本独立采样 B0×N）

### Q1. B2 比 B1 好，为什么还不能说明“变异反馈有效”？你加了哪些对照？

- **两个混杂因素**：(1) **花费**：B2 的 token 是 B1 的 2–4 倍（itertoolz 133K vs 35K），多花的 token 本身就可能带来提升；(2) **信号**：B2 相对 B1 多了“全部通过后继续迭代”这个环节，提升可能来自“多迭代几轮”，而不是来自变异信号本身。
- **BC（覆盖率反馈）** 控制第二点：同一张图、同样的终止条件和预算、同样的有效性检查，只把反馈从“存活变异体”换成“未覆盖的行 / 分支”，提示词结构对齐。B2 − BC 才是变异信号相对覆盖率信号的增益。
- **B0×8（等成本独立采样）** 控制第一点：把不少于 B2 的 token 花在 8 次独立生成上，按不涉及变异的信号挑一份（best）或取所有有效测试的并集（union）。N 是按“token 不少于 B2 均值”事先定的，不是看结果调的。
- **结果**（`results/m55_*`，3 个目标各 3 次）：itertoolz 上 B2 95.8% > BC 94.1% > union 92.8%；functoolz 上反过来，union 74.4% > best 67.0% > BC 63.3% > B2 62.4%。也就是说变异反馈的优势依赖目标，在 functoolz 上不如把同样的钱花在独立采样上。

### Q2. BC 在 dicttoolz 上 100% 行覆盖、100% 分支覆盖，变异得分却只有 91%。这说明什么？

- 覆盖率只衡量“代码有没有被执行”，不衡量“结果有没有被检查”。一个只调用函数、不做断言的测试也能拿满覆盖率。
- 作为**反馈信号**，覆盖率会**饱和**：满了之后就没有可反馈的内容，BC 第 2 轮就按规则停止了；变异测试此时还能指出 11–13 个存活变异体，信号仍然存在。
- 作为**奖励**，这意味着用覆盖率训练或选择，会在高覆盖区间失去区分度，并且鼓励“执行到但不检查”的测试。这也是 M9“代理指标可靠性”实验要量化的问题：覆盖率、LLM 评委与变异得分的相关性。
- 要补充的是，变异得分也有饱和和噪声问题（等价变异体设定了上限，§5.6 的奖励欺骗），所以不是“变异好、覆盖率差”，而是两者在不同区间各有盲区。

### Q3. functoolz 上 8 次独立采样的并集比 B2 高 12 个点，你怎么解释？这会怎样改变你的方法？

- **解释**：functoolz 难（`curry`、`memoize`、签名推断），B2 的大部分轮次在修复新加的失败测试（§5.8：15 轮中 11 轮），真正拿到变异反馈的轮次很少；而独立样本各自断言了不同的行为，失败的测试直接被有效性规则剔除，不消耗修复预算，并集自然覆盖更多行为。本质是**深度（迭代修改一份测试）和广度（多份独立测试）的权衡**，难的目标上广度更划算。
- **需要说明的代价**：union 有约 660 个测试，是 B2 的 6 倍多，测试运行和维护成本更高；“变异得分”没有对测试集大小做归一化，比较时要一起报告。
- **对方法的改变**：变异信号不一定要用在反馈上，也可以用在**选择**上：先独立采样 N 份，再按变异得分挑选或贪心精简测试集（选出能杀死同样多变异体的最小子集），最后再做一两轮变异反馈。这就是 M9 测试时扩展要比较的“验证器用于选择 vs 用于反馈”。样本已全部保存，计算按变异得分选择不需要再调用 LLM。
- **统计上的保留**：只有 3 个目标，任何差异都不显著（配对符号翻转检验的最小 p 值是 0.25），以上都只是假设，要在 M8 的 100+ 目标上验证。

## M8：主评测（11 个仓库、66 个目标）

### Q1. 你说“变异反馈比覆盖率反馈好”，证据是什么？统计上怎么做的？为什么每个目标只跑 1 次？

- **数据**（`results/m8_compare/compare.md`）：66 个目标上 B2 84.2%，BC 80.7%；按目标配对，B2 − BC = +3.4 个点，95% bootstrap CI [+1.1, +6.0]，符号翻转置换检验 p = 0.005，40 胜 17 负。两者 token 相近（70K vs 61K），流程、预算、有效性规则都相同，只差反馈信号。
- **统计单位是目标**：同一目标的多次运行共享目标难度，不是独立样本；目标之间的难度差（同一方法 30%–100%）远大于方法差异，所以先在目标内取均值，再对“各目标上的差值”做推断，配对消掉了难度。
- **为什么 1 次**：预算和时间有限时，推断的精度主要取决于目标数，而不是每个目标的重复次数——重复只能降低单个目标内的噪声，不能增加独立样本。M5.5 里 3 个目标 × 3 次的结论（functoolz 上独立采样胜过 B2）在 66 个目标上就不成立了。代价是单个目标上的结论不可靠，只能说总体层面。
- **其他控制**：所有方法在同一批里交错运行（模型版本变化对各方法影响相同）；目标筛选规则和剔除规则（变异测试 > 600 秒、mutmut 不兼容）都在看结果之前定下，并写在清单里。

### Q2. 汇总表里 union 的覆盖率比它的子集 best 还低，你怎么发现并处理的？

- **发现**：并集的覆盖率不可能低于其中任何一份——这是一个“不可能的数字”。逐个目标看 union 的有效性明细，16 个目标的 union 是 0 个有效测试，原因都是“未收集到”。
- **原因**：union 把 8 份样本放进同一次 pytest 运行，任何一份收集失败（语法错误、导入不存在的名字），pytest 就中断整个会话。这是我实现时的 bug：设计里 union 的定义是“各样本有效测试的并集”，实现却变成了“8 份放在一起重新判定”。
- **处理**：修正为只纳入单独筛查有有效测试的样本；样本都已保存，离线重评不花钱；原始日志不改，重评结果放在新目录，比较时显式排除旧变体；在设计文档里记录 bug 和修正。修正后 union 85.8%，与 B2 打平。
- **如果不修**：结论会变成“B2 比独立采样并集高 20 个点”，是一个错误而且对自己方法有利的结论——这类 bug 最危险，因为它不会让人想去查。

### Q3. 训练截止后创建的仓库（new 组）上，B1 掉了 16 个点，B2 只掉 4 个点。这能说明数据污染吗？

- **能说明的**：在 new 组上，单次生成（B0 58.1%）和只有 pytest 反馈的 B1（65.9%）明显更差，而 B2（81.3%）接近 old 组水平；B2 相对 B1 的优势从 +3.2 扩大到 +15.4。这与“模型对熟悉的代码记得行为，对陌生代码更依赖执行反馈”一致。
- **不能说明的**：两组仓库不是随机分配的，难度本身就不同——人写测试在 new 组上也只有 56.6%（old 组 73.3%），new 仓库多是重试 / 异步 / LLM 输出处理这类更难测的代码。所以这只是相关，不能当成“污染导致 old 组分数虚高”的证据。
- **更严格的做法**：在同一个仓库里比较训练截止前后新增的模块（控制住仓库风格和领域），或者对 old 组的代码做语义保持的改写（重命名、调整结构）后看分数是否下降；以及扩大 new 组规模（现在只有 4 个仓库、17 个目标）。
